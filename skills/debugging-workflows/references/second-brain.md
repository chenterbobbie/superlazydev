# Second-brain notes

Keep durable project notes small, searchable, and useful during future debugging. First inspect existing documentation and follow the repository's established location and format.

## Good notes

- Architecture landmarks and verified control or data flow, with source links.
- Local conventions that are easy to miss, such as test setup or error handling patterns.
- Reproducible failure modes and their verified causes or diagnostic clues.
- Commands confirmed to work in this repository, including relevant scope or prerequisites.

## Keep notes trustworthy

- Prefer updating an existing note over creating a duplicate.
- Mark uncertain information as unverified; remove or revise it when evidence changes.
- Add a date to details likely to become stale, such as commands or runtime behavior.
- Exclude secrets, personal data, speculative diagnoses, and temporary incident details with no future value.
- Persist notes only when requested or when the project already has a clear place for them.
